# 延迟差异

「延迟」这里指 **你说完 → 模型开始出声**（首响），以及 **打断是否跟手**。屏享是每秒一张 JPEG，画面理解另算，不是音频 RTT。

数字是 **量级**，不是本机实测。上线后用墙钟秒记在 README。

## 三条链路比什么

```
A  Gemini 官网 / AI Studio Live
   浏览器 ──WSS──► Google

B  本项目 MVP（官方 C2S 示例）
   浏览器 ──HTTPS──► VPS（仅页面+token，一次）
   浏览器 ──WSS──► Google     ← 通话走这条

C  LiveKit Cloud + Agent + Gemini
   浏览器 ──WebRTC──► LiveKit
   Agent  ──WSS──► Google     ← 媒体多一跳
```

还有一条 **不要当 MVP** 的：浏览器 → 你的 Python → Google（官方 `gemini-live-genai-python-sdk`）。音视频全程过 VPS，延迟通常 **明显差于 B**。

## 相对官网（A）

| 环节 | 本项目 B | 相对 A |
|------|----------|--------|
| 打开页面 | 多一次打到 VPS | 可忽略（只发生在进站） |
| 取 token | 多一次 `/api/token` | 进站多 ~0.1–0.5s，**不进**每句话 |
| 语音双向 | 与 A **同一类** C2S WSS | 首响往往 **接近**；可能慢 **几十到一两百毫秒**（实现/缓冲/网络） |
| 打断 | 同一套 Live VAD | 可接近；差在播放缓冲是否清干净 |
| 屏享 | 同一 API：JPEG ≤ 1 fps | 不比官网「更实时」；把静音也维持 1 fps 是为了 **不比官网更稀** |

**诚实口径：** 安静桌面 + 好网络，B 可以做到 **接近网页 Gemini Live**，不是「同一毫秒」。打不赢官方 App 的系统采集、回声消除和全球边缘。VPS 在欧盟、用户在亚洲时，**网页仍直连 Google**，通话延迟 **不**随 VPS 位置线性变差；只有 **第一次打开页面** 会经过那台机器。

## 相对 LiveKit 骨架（C）

| | B 本项目 | C LiveKit |
|--|---------|-----------|
| 通话跳数 | 浏览器 → Google | 浏览器 → LiveKit → Agent → Google |
| 首响 | 通常 **更短** | 通常 **更长**（多一跳转码/排队） |
| 弱网 | 普通 WSS，丢包恢复一般 | WebRTC 往往更稳 |
| 何时用 C | — | 阶段 2：弱网、多人、电话 |

选 B 当 MVP，就是用 **略好的延迟** 换 **少一个厂商**。若实测 B 在手机 4G 上经常卡，再评估 C。

## 相对串联 TTS（非本项目）

Whisper → 文本模型 → TTS：常见 **数秒** 级，且难真打断。本项目若做成那种体感，验收失败。

## 新 agent 实现时别把延迟做差

- 不要把 PCM 先传到 VPS 再转 Google（那是另一份官方示例）  
- 出声后用户插话：立刻停 `AudioPlayer`（官方示例有 `interrupt`）  
- 屏享保持 1 fps；不要为省钱改成静音 0.3 fps（那是「画面更钝」，不是音频延迟）  
- token 短时缓存，避免每句话重新 `/api/token`
